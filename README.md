# Expense Sharing Service

A backend service for tracking shared expenses among groups of friends like a simplified Splitwise. Built as part of the Decentro SDE Intern assignment.

Demo: **[Watch the Video Demo](https://youtu.be/yiK8TZGvwns)**

## Features

### Core Features
- [x] User management (create, list, get)
- [x] Group management with member tracking
- [x] Expense recording with equal split among members
- [x] Balance calculation between users with mutual debt netting
- [x] View expense history per group

### Bonus Features
- [x] **Custom Split** — Unequal expense splits with validation
- [x] **Settlement Tracking** — Record payments between users to settle debts
- [x] **Docker Support** — One-command deployment
- [x] **Unit Tests** — 22 comprehensive tests covering all critical paths

### Product Enhancement Features
- [x] **Smart Settlement Suggestions** — Greedy algorithm to minimize the number of transactions needed to settle all debts
- [x] **Expense Analytics** — Category-wise spending insights, per-member breakdown, and group statistics

## Database Schema Explanation

### Tables Overview

#### `users`
Stores user information.

| Column | Type | Constraints |
|--------|------|-------------|
| id | Integer | Primary Key |
| name | String(100) | NOT NULL |
| email | String(255) | UNIQUE, NOT NULL |
| created_at | DateTime | Default: now |

#### `groups`
Stores group/trip information.

| Column | Type | Constraints |
|--------|------|-------------|
| id | Integer | Primary Key |
| name | String(100) | NOT NULL |
| created_by | Integer | FK -> users.id |
| created_at | DateTime | Default: now |

#### `group_members`
Many-to-many junction table linking users to groups.

| Column | Type | Constraints |
|--------|------|-------------|
| id | Integer | Primary Key |
| group_id | Integer | FK -> groups.id, CASCADE |
| user_id | Integer | FK -> users.id, CASCADE |
| joined_at | DateTime | Default: now |

**Unique Constraint:** `(group_id, user_id)` — prevents duplicate memberships.

#### `expenses`
Records each expense added to a group.

| Column | Type | Constraints |
|--------|------|-------------|
| id | Integer | Primary Key |
| group_id | Integer | FK -> groups.id |
| paid_by | Integer | FK -> users.id |
| amount | Numeric(10,2) | NOT NULL, > 0 |
| description | String(255) | NOT NULL |
| split_type | String(20) | 'equal' or 'custom' |
| category | String(50) | Nullable |
| created_at | DateTime | Default: now |

#### `expense_splits`
Stores pre-computed splits for each expense — who owes what.

| Column | Type | Constraints |
|--------|------|-------------|
| id | Integer | Primary Key |
| expense_id | Integer | FK -> expenses.id, CASCADE |
| user_id | Integer | FK -> users.id |
| amount_owed | Numeric(10,2) | NOT NULL |
| is_settled | Boolean | Default: false |
| created_at | DateTime | Default: now |

#### `settlements`
Records payments made to settle debts.

| Column | Type | Constraints |
|--------|------|-------------|
| id | Integer | Primary Key |
| group_id | Integer | FK -> groups.id |
| paid_by | Integer | FK -> users.id (debtor) |
| paid_to | Integer | FK -> users.id (creditor) |
| amount | Numeric(10,2) | NOT NULL |
| note | String(255) | Nullable |
| created_at | DateTime | Default: now |

### Key Design Decisions

1. **`expense_splits` as a dedicated table**  
   Instead of recalculating splits on every balance request, we store them upfront. This makes balance queries fast and consistent. The payer is intentionally excluded since they don't owe themselves.

2. **`Numeric(10,2)` for money, not `Float`**  
   Floats have precision errors (e.g., `0.1 + 0.2 = 0.30000000000000004`). For financial data, `Decimal` ensures exact arithmetic.

3. **`is_settled` flag on splits, not deletion**  
   We never delete settled splits — we just mark them. This preserves audit history.

4. **Partial settlement handling**  
   When a settlement is partial, we mark the original split as settled and create a new split for the remainder. This keeps the math consistent.

5. **CASCADE deletes on `expense_splits`**  
   If an expense is deleted, its splits are auto-cleaned. No orphan records.

6. **UNIQUE constraint on `(group_id, user_id)`**  
   Prevents accidentally adding the same user twice to a group.

## Business Logic Explained

### Balance Calculation Algorithm

```
1. Fetch all unsettled expense_splits joined with expenses
2. For each split:
   debtor   = split.user_id
   creditor = expense.paid_by
   accumulate: balances[(debtor, creditor)] += amount

3. Subtract settlements from corresponding pairs

4. Net out mutual debts:
   If A owes B 400 AND B owes A 100
   -> Net: A owes B 300 only

5. Format output: { debtor: { owes: { creditor: amount } } }
```

### Smart Settlement Suggestions Algorithm

The goal: **minimize the number of transactions** to settle everyone's debts.

```
1. Compute net balance per user:
   net[user] = (total received) - (total owed)
   
2. Split users into:
   creditors (net > 0): need to receive money
   debtors   (net < 0): need to pay money
   
3. Greedy matching:
   While both lists non-empty:
     - Pick largest creditor and largest debtor
     - settlement = min(creditor_amount, |debtor_amount|)
     - Record: debtor pays creditor this amount
     - Reduce both balances
     - Remove from list if balance hits 0
```

**Example:**  
If Ankit owes Rs. 600 total, Mohit is owed Rs. 400, Rahul is owed Rs. 200:  
-> Suggestion: Ankit pays Mohit Rs. 400, Ankit pays Rahul Rs. 200 (2 transactions instead of 3+)

## Product Enhancement Features

### 1. Smart Settlement Suggestions

**Why I built this:**  
At the end of a trip, people often make redundant payments (A pays B, B pays C, C pays A). This wastes time and money on transfer fees.

**How it solves the problem:**  
Provides a single optimized list of "who should pay whom" to settle all debts with the fewest transactions possible.

**Design decision:**  
Used a greedy algorithm. It's O(n log n), simple to reason about, and gives near-optimal results.

**Tradeoff:**  
Greedy doesn't guarantee the absolute minimum in all cases (the general problem is NP-hard), but it's fast and good enough for real-world group sizes (typically 3-20 people).

### 2. Expense Analytics

**Why I built this:**  
Users want insights: "where did all our money go?" not just raw expense lists.

**How it solves the problem:**  
Provides aggregated views: category-wise breakdown, per-member contributions, largest expense, and group totals.

**Design decision:**  
Added optional `category` field on expenses (Food, Transport, Hotel, etc.) for flexible categorization without ML complexity.

**Tradeoff:**  
Manual categorization vs. auto-categorization. Chose manual for simplicity (auto-categorization would need NLP on descriptions).

## Assumptions Made

1. **Users must be added to a group before expenses can be recorded** (a group needs at least 2 members).
2. **Equal split by default** — If `split_type` is not provided, expense is split equally among all group members.
3. **Payer doesn't owe themselves** — Excluded from `expense_splits`.
4. **Email uniqueness** — Each user must have a unique email (basic identity guarantee).
5. **No authentication** — Assignment scope doesn't require JWT/auth. Would add in production.
6. **Single currency** — All amounts are in same currency (assumed Rs.). Multi-currency would need exchange rates.
7. **Custom splits must sum exactly** — `sum(custom_splits.amount) == expense.amount` (strict validation).
8. **Settlements reduce balance, not delete history** — Original expense splits are preserved for audit.

## Architecture & Design Decisions

### Layered Architecture
```
HTTP Request -> Router -> Service -> Model -> Database
              (thin)  (logic)  (ORM)   (SQLite)
```

- **Routers** only handle HTTP concerns (status codes, request parsing).
- **Services** contain ALL business logic. Routers never query DB directly.
- **Models** define database structure only.
- **Schemas** validate input/output independently from DB models.

**Why this matters:** Easy to test (services are pure functions), easy to swap database, easy to add new API formats (e.g., GraphQL) without rewriting logic.

### Key Design Decisions

| Decision | Reasoning |
|----------|-----------|
| FastAPI over Flask/Django | Auto API docs, async support, Pydantic validation built-in |
| SQLite over PostgreSQL | Zero setup for reviewers; easy to swap via SQLAlchemy |
| `Decimal` for money | Exact arithmetic, no float precision bugs |
| Pre-computed splits | Faster balance queries, audit trail |
| Greedy settlement | Simple, fast, good enough for real groups |
| Global exception handler | Consistent error format across all endpoints |
